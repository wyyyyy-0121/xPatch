# 原始 CPU 验收的完整冷启动计时修订

2026-11-06 的本地源码复核发现：原 `delivery.replay()` 从函数入口开始计时，报告文字却包含了全新 Python 进程启动。函数入口之前的解释器启动、库导入及启动适配器开销没有计入，不能以这段耗时证明完整冷启动不超过 60 秒。

独立 `scripts/original_delivery_timing_runtime.py` 只在未来本地验收子进程安装。它使用 Linux `/proc/<pid>/stat` 的创建时刻与 `CLOCK_BOOTTIME`，从内核进程创建计至第一个成功预测完成持久化；覆盖导入、准入、模型加载、输入准备、预热和状态落盘。创建时刻按内核 tick 截断会保守增加不足一个 tick 的时间。计时不依赖会在 WSL 校时后改变的墙钟创建 epoch。

每个退出与恢复进程保存 boot ID、PID、创建 tick、时钟频率和首个落盘时刻。最终报告取所有进程的最大完整耗时；原函数内计时保存为 `engine_cold_load_seconds`。测量缺失、身份重复、策略不符或记录不一致均不能通过。60 秒冷启动门槛、256 个起点、暖推理 p95 不超过 1 秒及原有其他门槛保持原值，适配器只可使验收更严格。

冻结引擎、FP32 数值策略、输入提速策略和包复制修订均保留原身份。训练、预测值、研究放行条件及 100 小时绝对截止不变。修订源码、策略和本说明进入 CPU 包的证据文件。合成双进程检查只验证工程行为；实际模型仍须完成真实验收，不能用合成结果替代。

安装程序核验本地接收者的内核创建身份、原绑定、代码和纯等待阶段，在原钩子与历史收据保留后原子更新未来子进程入口。当前接收者已导入代码和云端训练均不加载本修订。后续研究准入须核验真实完整计时，不能用原函数计时或缺少测量的历史报告放行。

实际入口检查还确认：CPython 用 `-m fusion.next.local_package` 执行时，会创建第二套模块全局变量，导致规范模块内已安装的 FP32、复制和证据适配器没有进入该入口。未来子进程因此将这一条模块入口转至独立 `scripts.original_cpu_package_entry`，保留原参数和调用顺序，调用已安装适配器的规范打包模块。只重定向这一条入口；其他 `-m` 模块仍按原方式执行。此桥接文件的哈希进入同一计时与入口策略，其源码随包保留。冻结打包算法本身不改动。
