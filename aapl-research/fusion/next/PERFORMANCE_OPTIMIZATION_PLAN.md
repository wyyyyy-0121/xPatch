# RTX 5090 两轮训练与性能调度修订

本修订在首次正式开发评分前生效。用户最新决定为“保留原全部研究范围，每个完整候选只做 2 轮”，替代上一版十轮安排。此前取消总 24 卡小时和各计算包小时上限的授权继续有效；两轮是训练量限制，目前没有另设租赁费用硬上限。主计划文件及其 SHA 保留，数据、评价、候选和研究停止条件继续执行。

目标是缩短固定研究范围的实际工期，并记录预测效果与计算成本。调度按每秒有效窗口和端到端耗时选择批量与精度，记录 GPU 功耗、温度、利用率和显存；本次调整不涉及超频或系统功率限制。

## 训练范围与两轮的定义

保留全部预定搜索机会：LightGBM 24、xPatch 16、PatchTST 16、简单融合 12、冻结融合 24、多股票/AAPL 配对 8、LoRA 8。保留 13 个前向 OOF 季度、三个主验证季度、2026/2027/2028 三种子和七组机制对照。

神经模型完整预算是各折自身合法历史数据的两个均衡覆盖轮所对应的样本曝光量。更新数为 `ceil(2 × 该折均衡轮样本数 / 该模型 batch)`，仅允许最后一个 batch 的向上取整。适配 AAPL 的尾段包含在两轮内：最多 20% 用于适配时，共享阶段约 1.6 轮，不再额外增加 0.4 轮。AAPL 单股配对沿用多股侧的样本和更新预算，因此会重复使用较少的单股窗口，须单列其真实覆盖与复用次数。

连续晋级仍为 10% → 30% → 100%，对应约 0.2 → 0.6 → 2 个等价轮。首档不能宣称已经完整遍历历史。每档接续同一个优化器、采样顺序和随机状态；未晋级候选按预定档位停止。

覆盖采样器将全部合法窗口按股票和交易日均衡排列；短交易日补齐为等长日槽，股票之间额外日槽逐轮轮换。记录去重覆盖、完整覆盖轮、重复曝光和训练损失，重复样本不计作新增窗口，相邻分钟也不当作统计独立样本。较早 OOF 折使用各自预算，不套用最大历史段的更新数。

Ridge/LightGBM 使用全部合格窗口及股票/交易日均衡权重；两轮限制对应神经模型，不把树的 1,000 棵上限改写为两个训练轮。Ridge 分块累计充分统计量，避免额外复制全量双精度矩阵。

## 5090 上已经测得的吞吐

硬件为 RTX 5090 / 32 GB，实际可见显存 32,607 MiB；CPU 配额 25 核、cgroup 内存 90 GiB。截图报价为 ¥2.88/小时，费用估算按该报价计算，供应商账单另行核对。

Chronos/LoRA 的原始端到端批量测试使用 2021—2022 年数据，比较 FP32/BF16 与 batch 64/128/256/512，冻结模式还测试了 1024。冻结模式 batch 256 + BF16 约 1,896 窗口/秒，LoRA 约 1,047 窗口/秒；扩大到 512 使冻结模式变慢，LoRA 则显存不足。正式 Chronos/LoRA 选 batch 256，并重新执行对应数值与 900 秒持续压力准入。

新原生模型测试覆盖每个配置 65,536 个窗口，最大历史窗口 240。CPU 提前准备两个 batch，与 GPU 计算重叠；各组顺序执行和预取执行复用相同权重、数据顺序与随机状态，所有成功比较的训练损失序列完全一致。

| 模型 | batch | 顺序执行，窗口/秒 | 预取执行，窗口/秒 | 该档吞吐提升 |
| --- | ---: | ---: | ---: | ---: |
| xPatch | 256 | 7,187 | 11,525 | 60.4% |
| xPatch | 512 | 7,479 | 10,416 | 39.3% |
| xPatch | 1024 | 5,600 | 7,392 | 32.0% |
| PatchTST | 256 | 4,358 | 6,065 | 39.2% |
| PatchTST | 512 | 4,310 | 6,639 | 54.0% |

据此选择 xPatch batch 256、PatchTST batch 512。PatchTST 512 的该次峰值设备显存约 13.8 GB；1024 被资源检查拒绝，失败保留。所列吞吐是最大形状训练片段，不包含完整研究的全部推理、检查点和等待时间，不能直接换算最终完工日期。

## 调度实现与资源分配

| 工作 | 运行配置 | 调度安排 |
| --- | --- | --- |
| Chronos 冻结分支 | batch 256；编码器固定 FP32 | 跨股票的缓存缺失合并成一次编码调用，填充一次后供相同输入和权重复用 |
| 冻结融合训练头 | FP32 或 BF16 | 依据真实缓存复用端到端计时选择；FP32 至少快 5% 时使用 FP32 |
| Chronos LoRA | batch 256、BF16，rank 8/16 | 单 GPU 作业；不复用冻结表示缓存 |
| xPatch | batch 256、BF16 | 一个 CPU 生产线程、深度 2 的有界预取与 pinned memory |
| PatchTST | batch 512、BF16 | 相同的有界预取；正式 batch 还须通过精度与资源准入 |
| Ridge / LightGBM | 全窗口，最多 8 个线程 | 一个 CPU 搜索/OOF 工作流与 GPU 流并行，避免竞争 CPU 与内存 |
| 保存、评分与恢复 | 每 1,000 更新及晋级边界保存 | 原子收据保留当前及前一完整检查点；预取不推进已提交采样器 |

GPU 运行的 PyTorch CPU 池为 2 线程，另有一个 batch 准备线程。F2 独立进程将 CPU 计时分配到核 0—7、GPU 驱动到 8—24；正式训练可使用 0—24，仍只保留一个 CPU 工作流和一个 GPU 工作流。本地新研究总分配继续不超过 18 个逻辑线程。

预取只提前执行取窗、OOF 查询、掩码和内存准备；模型、随机操作、优化器和缓存编码保持在 GPU 主流程。提交采样器仅在消费 batch 时前进，已有测试覆盖启用预取后的连续/中断恢复一致性。缓存键绑定权重、输入字段、窗口、时间、编码器精度、训练头精度和代码身份；半精度存储必须通过数值门槛。LoRA 和随机骨干不能复用预训练表示。

当前已实现并测试 CPU/GPU 重叠、单生产线程预取、跨股票缓存合批以及各模型独立 batch。双 GPU 训练进程并发和 `torch.compile` 仍未实施或准入，不计入性能收益。云端单进程 RSS 初始上限 64 GiB、本地 8 GiB，容器内存至少保留 4 GiB，设备显存保持在 85% 以内。用吞吐与实际耗时评估调度，不能要求所有模型阶段都有相同利用率或功耗。

## 执行顺序

批量与预取测试 → 本地/云端测试 → 最终配置的精度、恢复及 900 秒 GPU 压力运行，同时完成全量 CPU 测量 → 完整成本投影 → 冻结逐折两轮清单 → F3 单模型/OOF → F4 融合与迁移 → F5 LoRA/种子/机制 → F6 固定确认 → 条件式 F7 → F8。

云端 `cloud_driver` 已按新配置启动。它保存旧版报告及代码，完成最终 F2、两轮预算冻结并执行 F3；入口有文件锁，失败时保留日志和检查点并停止推进。F3 完成后该入口结束，后续按阶段继续 F4/F5。任何正式实验只接受与冻结源代码身份一致的配方。

原计划的共同起点、时间隔离、至少 1% 改善、最强单模型和简单融合对照、种子稳定性、Q2 确认及最终统计要求继续有效。目前没有正式预测改善结论，2026Q3 行情数值未访问；若 F5 缺乏稳定增量，按原计划交付结果与可运行系统。训练次数和损失下降不能替代这些证据。
