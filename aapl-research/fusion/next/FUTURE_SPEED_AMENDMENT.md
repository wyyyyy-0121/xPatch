# 后续进程输入准备提速

用户要求开始开发速度优化，并将验证有效的改进接到后续任务。当前云端进程继续运行，未为本次优化中断、重启或修改其配置。每两小时复查一次，仅在有重要变化时通知。

## 已实现的改进

原 `Panel.windows` 每个批次重复对背景序列进行成交量季节性扣除、训练折标准化和裁剪。外部适配脚本为每个背景股票、训练折缩放器和信息范围预先计算同一逐行变换，后续批次只索引对应历史窗口。

只对不可写的开发期内存映射启用；实时输入和可写面板使用原路径。缩放器内容、面板身份或信息范围变化时不能命中旧缓存。缓存有 256 MiB 上限和淘汰规则，单条序列超过上限时使用原路径。计算变换不拟合任何新参数、不读取标签，也不改变原窗口、标签和时间边界检查。

原模型引擎身份仍为 `fb0a03b4841e9bde2b555440214b2b4308bc89e8ce2f3473b22a73b6ffd063cb`。独立速度策略为 `0c433a556af0a5d944c7a6afdfdbda35b9a7ac372610b7492295dcc487f06fab`，原 FP32 推理策略继续独立核验。训练轮次、更新数、股票、季度、种子、采样器、随机数、优化器、精度、模型及科研门槛保持原值。

## 实测与验证

2026-11-05 在本地和现有云端 CPU 各验证 36 组真实数据批次，覆盖三个训练折、48/96/240 分钟窗口、OHLCV/close 两种输入、训练及无标签推理路径。所有张量逐项完全一致。计时使用每次更新的随机有效起点，并在同一批输入上交替两条路径，避免只反复读取一个固定窗口。

| 机器 | 256 样本、240 分钟窗口的准备时间 | 吞吐倍数 |
| --- | --- | --- |
| 本地两个 CPU 核心 | 原约 9.0–10.2 ms，优化约 6.4–7.1 ms | 1.41–1.43 倍 |
| 云端两个 CPU 核心 | 原约 17.4–17.9 ms，优化约 11.0–11.1 ms | 1.56–1.63 倍 |

云端首次计算约 0.14 秒，约 19–21 个批次抵消初始化开销。这些数字只证明 CPU 输入准备提速；GPU 完整训练、首次基础模型表示缓存填充以及最终交付的总加速尚未测定。

相关 38 项检查通过，包含 xPatch、PatchTST 实际短训练与断点恢复：最后损失、模型参数及缓冲区、采样器状态、随机数状态均与原路径完全一致。还覆盖缩放器失效、缓存淘汰、实时面板回退、标签边界，以及仅允许在本地等待状态设置未来子进程入口。

速度策略及两台机器的基准记录位于忽略目录 `outputs/fusion_next/performance/`；原脚本副本随独立策略保存，正式回传必须校验其哈希。模型引擎目录内没有新增 Python 文件，因此原源码身份不受本次脚本影响。

## 实际接入状态

本地等待云端的收尾进程仍为原进程。已经设置其未来 Python 子进程的启动钩子，并在真实独立解释器中确认适配成功；之后的本地研究复核、批量预测和部署验收子进程会加载提速策略。CPU 推理包示例入口保持原独立数值入口，不依赖该开发期提速钩子；实时输入本来也走原路径。

云端新启动入口已上传且在隔离 CPU 进程通过策略核验：

```bash
bash cloud/run.sh scripts/start_fast_fusion.py scripts/run_fusion_100h.py
```

现有 F4/F5 队列是同一 Python 进程，无法在不改变活进程的情况下仅给下一个函数调用更换实现。因此该进程仍用原实现，不能声称当前云端训练已经提速。只有在确实需要启动下一个独立云端进程、原进程已自然结束或另有授权恢复时才使用新入口；禁止同时启动第二份训练，也不为启用本优化主动中断当前队列。原 100 小时绝对截止继续有效。

本次还修复了外部范围报告的一处路径变量覆盖：读取 FP32 重算记录后，阶段范围绑定必须继续使用范围收据路径，不能误用最后一份结果路径。新增包含真实重算结构的回归检查；未修改原模型或放行规则。
